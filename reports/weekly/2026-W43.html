Strata kontra llama.cpp: pierwszy porównywalny MoE-cache A/B na jednej V100 PCIe 32 GB

WARTO ODTWORZYĆ · bezpośrednia V100, nie porównywać MTP jak identycznych runtime’ów

Metoda (18.10): Tesla V100-PCIE-32GB, SM70, PCIe Gen3 ×4 (~3,3 GB/s), i7-13700KF, 16 GB RAM, CUDA 12.9. Ten sam Coder IQ1_M w dwóch GGUF, streaming single client, greedy, 256 tokenów wyjścia; prompty 256/1000/4096 tok., po 3 próby. Autor przypiął Strata 0.1.41 i llama.cpp b11718.

Decode (256/1000/4096 tok. promptu): llama.cpp cały model w VRAM 42,9 / 42,4 / 41,7 tok/s; llama.cpp --cpu-moe --moe-cache-mib 24000 przy 100% ekspertów w cache GPU 35,2 / 37,5 / 37,3. Strata bez vision i bez MTP 70,9 / 66,7 / 60,4; z MTP i wszystkimi ekspertami resident 101,2 / 98,5 / 98,0. TTFT przy 4096 tok.: 9,8 s / 13,2 s / 3,4 s (Strata).

Wyjaśnienie: cache llama.cpp w tym przypadku tworzył ~50 odcinków grafu na token zamiast dwóch, stąd przy 100% resident experts był wolniejszy od zwykłego GPU load. Cache 20 GB nadal dawał 99,1% hit, ale przy 16 GB 96,4% hit powodował czterokrotnie większy ruch, a przy 8 GB decode ~5 tok/s. Nie jest to pomiar „2,4× lepszych kerneli”: Strata ma również dedykowane optymalizacje i MTP, którego odpowiadający model w llama.cpp nie miał. Bez MTP przewaga w tej konkretnej konfiguracji nadal wynosi ok. 1,5×.

Single V100: najpierw porównaj prawdziwie resident model z offloadem i zmierz graph splits, PCIe i acceptance. Cache ma sens dopiero, gdy zyski z unikania transferów przewyższą jego własny narzut. Benchmark nie dowodzi wyników Qwen3.6/3.8.

Rekomendacje tygodnia

1. Przypnij dokładny SM70 toolchain

Dwa buildy llama.cpp z CUDA 12.8 / 12.9 przy tych samych wagach. Rozdziel compile target, load i pierwszy token. Bez tego OOM nie mówi nic o budżecie VRAM.

2. Sprawdź resident vs cache MoE

Nie włączaj cache „na zapas”, gdy eksperci mieszczą się w 32 GB. Rozpoznaj ratio cache hits, graph splits i PCIe RX; aktualne SLRU nie zmienia tej zasady.

3. Nie aktualizuj w ciemno NInfer

geoffwatts artifact v3 nadal nie działa. JimmyMax używa SM70 image, nie CUDA13 :latest. Porównuj forków na tym samym GGUF i z wyłączonym MTP jako kontrolą.

4. KV i server API to correctness

Sprawdź SWA slot resume, concurrent shared prefix i Responses SSE/Anthropic sampling. Przy złym KV 10% TG wzrostu jest bez znaczenia.

5. Memory migration tylko po backupie

OpenViking 0.5.2: schema/imports/management-key/WM default, write(create)=replace. Odtwórz backup w izolacji i sprawdź szyfrowanie przed pierwszym startem.

6. Przestań mierzyć tylko t/s w voice

Voxtral STT + mały local LLM + Soprano TTS: mierz TTFA, przerwania i opóźnienia częściowe, a nie sam przepływ modelu. Native Moshi to osobna klasa.

3 rzeczy do przetestowania w homelabie

A · Single V100: Qwen3.6 long-context

Qwen3.6-35B-A3B jeden GGUF, Strata vs llama.cpp, CUDA 12.8 i 12.9 (osobno); PP/TG/TTFT przy 4K,16K,32K,64K. Zapisz KV dtype i exact commit, MTP=0 jako kontrola. Wymagaj też poprawnych odpowiedzi po cache restore.

B · Qwen3.8-Flash-Next VRAM budget

llama.cpp przed/po #30965, SLRU on/off, ub2048/4096. Loguj CUDA+CUDA_Host compute buffers, peak VRAM, OOM, PP/TG i ekspertów hits/misses. Jeśli model wymaga RAM, dodaj host RSS i PCIe H↔D.

C · Głos 100% lokalny z barge-in

Voxtral GGUF streaming STT → Q4 LLM → Soprano 80M (lub Qwen3-TTS), z Silero VAD. Loguj koniec mowy→ASR final→LLM TTFT→first audio oraz zrywanie TTS. Zmierz CPU-only TTS i reakcję podczas długiego generowania; porównaj qualitatively z Moshi native S2S.

Trend tygodnia

Era „najwyższego token/s” ustępuje erze przewidywalnego stanu systemu.

Tematem wspólnym są granice pamięci: eksperci MoE mieszczą się w VRAM albo wchodzą w kosztowne PCIe, cache GPU potrzebuje stabilnej polityki SLRU, Qwen3.8 zużywa gigabajty na tymczasowy indexer/mask, a KV checkpoint może albo oszczędzić minutę prefillu, albo spowodować błędną odpowiedź. Bezpośredni test V100 pokazuje, że ten sam typ „optymalizacji” może obniżyć wydajność, gdy nie trafia w problem właściwego workloadu.

Nowa jakość local self-hosting nie jest też wyłącznie tekstowa. llama.cpp ma streaming transcription WebSocket i TTS endpoint, ale kaskadowe voice agents nadal potrzebują osobnego VAD, anulowania audio, bezpieczeństwa sesji i jasnej polityki danych. OpenViking 0.5.1/0.5.2 przypomina o tym mocno: zmiana jednego domyślnego flagu może odwrócić semantykę zapisu lub odsłonić migrowane dane. Dla pojedynczej V100 32 GB PCIe najlepsza strategia to repeatable A/B, pinowana CUDA, poprawny KV i jawna pamięć, nie ekstrapolacja wyników Blackwell.
